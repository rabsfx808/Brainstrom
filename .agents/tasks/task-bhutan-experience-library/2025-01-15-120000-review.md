# Bhutan Travel Experience Library — greenfield Next.js application

A full-stack travel planning application for Bhutan built with Next.js 14, offering destination browsing, tour package exploration, an itemized cost calculator, and a preference-based package recommender. The implementation delivers eight page routes, a static data layer for destinations/tours/hotels/vehicles/food/experiences, two computation engines (calculator and customizer), shared UI components, and 32 unit tests.

**Watch for:** Tour and experience pricing in the calculator ignores group size (confirmed), the customizer's cost estimate omits mandatory fees like SDF and visa creating a misleadingly low total (confirmed), the "moderate" budget tier maps to "premium" tours with no differentiation (confirmed), and the candlelight dinner has a pricing ambiguity where `$120/per_person` is described as "per couple" in the data (confirmed).

## High-level view

The calculator correctly handles per-person multiplication for SDF, visa, flights, and food, but tours and experiences are priced as flat sums regardless of party size. A 2-person trip selecting a $3,500/person tour adds only $3,500, not $7,000. This makes the "grand total" unreliable for any group.

The customizer's `estimatedTotal` is labeled "per person" in the UI but the breakdown includes `tour.pricePerPerson` alongside absolute costs (hotel total, vehicle total). It also entirely omits SDF ($200/day/person) and visa fees, which for a 10-day trip would add $2,040 — a 15-25% undercount. The scoring algorithm itself is sound, but the financial output misleads.

The data layer has one significant inconsistency: the candlelight dinner charges `pricePerPerson: 120` and is used in the calculator with per-person multiplication, yet its own `dietaryNotes` says "$120 per couple." This will either double-charge couples or under-charge solo diners depending on which interpretation is correct.

The "moderate" budget preference in the customizer maps to `getBudgetTier("moderate") => "premium"` and `getHotelStarRating("moderate") => 3`. So a moderate-budget user gets premium-tier tours ($2,500-$3,500/person) paired with 3-star hotels — a mismatch that yields no genuinely budget-friendly option.

All listing pages are client components with `"use client"` despite having no interactivity beyond filtering. The destinations and tours detail pages correctly use `generateStaticParams` for static generation, but their parent listing pages ship all data to the browser in the JS bundle — the full 1,100-line tours array included.

1. **Tours/experiences not multiplied by persons** — `calculateTours` and `calculateExperiences` sum prices without multiplying by `params.persons`. The itemized line items show `quantity: 1` regardless of group size. Multiply by persons or document clearly that these are per-group costs.
2. **Customizer omits SDF + visa in estimate** — `getRecommendations` builds `estimatedTotal` from tour + hotel + vehicle + experiences + food, missing the mandatory $200/day/person SDF and $40/person visa. Add these to the breakdown or flag the estimate as "excluding government fees."
3. **Candlelight dinner pricing contradiction** — `pricePerPerson: 120` but dietary notes say "$120 per couple." Resolve by either changing to `pricePerPerson: 60` (making the couple cost $120) or updating the description.
4. **Moderate budget maps to premium tours** — `getBudgetTier("moderate")` returns `"premium"`, giving moderate-budget users the same tour pool as premium users. Either add a "standard" tier to tours data or remap moderate to filter by price ceiling.
5. **Customizer hotel selection is deterministic first-match** — `matchingHotels[0]` always picks the same hotel for a given star rating. Consider rotating or scoring hotels by location match to the selected tour.
6. **Large client bundles from `"use client"` listing pages** — Destinations, tours listings, and all filter pages ship full data arrays to the client. Convert to server components with client filter islands, or use `searchParams` for server-side filtering.
7. **Vehicle selection gap for groups 5-8** — `selectVehicleByGroupSize` looks for `category === "Premium" || category === "Luxury SUV"` for groups 5-8, but the Luxury SUVs seat only 5-7 and Premium vehicles seat 5. A group of 6-8 people won't physically fit. Use capacity-based filtering instead.

## Calculator arithmetic gaps around group size

The calculator applies per-person multiplication inconsistently. SDF, visa, flights, and food correctly scale by `params.persons`. But `calculateTours` sums `tour.pricePerPerson` without multiplying by the person count:

```typescript
export function calculateTours(tourIds: string[]): number {
  return tourIds.reduce((sum, id) => {
    const tour = tours.find((t) => t.id === id);
    return sum + (tour ? tour.pricePerPerson : 0);
  }, 0);
}
```

The field is named `pricePerPerson`, implying it should be multiplied by the group size. The itemized output pushes `quantity: 1` for each tour. The same pattern appears in `calculateExperiences` — `exp.price` is summed without considering how many people participate. Meanwhile `calculateFood` correctly multiplies by persons. This asymmetry means a 4-person trip selecting the Premium Honeymoon ($3,500/person) shows $3,500 total for tours rather than $14,000.

## Customizer's misleading cost estimate

The `getRecommendations` function builds `estimatedTotal` as:

```
tour.pricePerPerson + hotelCost + vehicleCost + experiencesCost + foodCost
```

Two problems compound here. First, SDF ($200/day/person) and visa ($40/person) are absent — these are mandatory Bhutan entry costs that dominate the budget for longer trips. A 10-day luxury honeymoon at $200 * 10 = $2,000 SDF alone is a substantial omission. Second, `hotelCost` uses `tour.duration - 1` nights (reasonable, since you don't pay for the departure night), but `vehicleCost` uses `tour.duration` full days. The food cost sums `pricePerPerson` without multiplying by group size (same issue as the calculator).

The UI labels this as "Estimated Total: $X/person" but it contains absolute costs (vehicle rental for the whole vehicle, not per-person). This hybrid of per-person and absolute costs in one number is misleading.

## Data integrity: candlelight dinner pricing

In `src/data/food.ts`, the candlelight dinner entry has:

```typescript
pricePerPerson: 120,
// ...
dietaryNotes: "Price is per couple ($120 per couple)."
```

The field name says per-person, the description says per-couple. The calculator's `calculateFood` multiplies `pricePerPerson * persons`, so a couple pays $240. If the intended price is $120/couple, the field should be `60` per person, or the data model needs a `priceType` field (similar to the experiences model which has `per_person | per_couple | per_day`).

## Budget tier collapse removes a meaningful gradient

The customizer accepts three budget levels but collapses them to two tour tiers:

```typescript
function getBudgetTier(budget: string): "premium" | "luxury" {
  if (budget === "luxury") return "luxury";
  return "premium";
}
```

A user selecting "moderate" ($2,000-$3,000/person range shown in the UI) receives the same tour pool as "premium" — tours ranging from $2,500 to $3,500/person. The only differentiation is the hotel star rating (3-star for moderate, 4-star for premium). Since the tour price dominates the estimate, moderate and premium users see nearly identical total costs, making the budget selector feel broken.

## Vehicle selection logic doesn't respect capacity

`selectVehicleByGroupSize` for groups of 5-8 people searches for vehicles by category name:

```typescript
} else if (groupSize <= 8) {
  return vehicles.find(
    (v) => v.category === "Premium" || v.category === "Luxury SUV"
  );
}
```

The first match in the data is `land-cruiser-prado` (capacity 7, category "Luxury SUV"). For a group of 8, this vehicle doesn't physically seat everyone. The logic should filter by `v.capacity >= groupSize` instead of by category label.

## Client-side data bundle size

Every listing page (`"use client"`) imports the full data arrays. The tours array alone is 1,100+ lines of TypeScript with detailed itineraries for 10 packages. This entire array ships in the client JS bundle even though the page only displays names, prices, and short descriptions. For a content-heavy catalog site like this, server components with client-side filter islands (or `searchParams`-based server filtering) would keep the initial JS payload significantly smaller. The detail pages already use `generateStaticParams` correctly — the listing pages could follow a similar static pattern with URL-based filters.

## Test coverage shape

The 32 tests cover the calculator's individual functions well and verify the customizer's scoring and hotel/vehicle matching. Gaps worth noting:

Not tested: the candlelight dinner pricing edge case, behavior when `params.persons` is 0 or negative, interactions between the calculator and data layer when IDs don't match across modules (e.g., selecting a tour ID that exists in tours but referencing a hotel room type that doesn't exist on the selected hotel), and the UI pages have no component or integration tests.
